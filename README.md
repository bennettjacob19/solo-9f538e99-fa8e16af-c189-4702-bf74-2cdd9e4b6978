# 磁带巡检与灾备恢复演练（Flask）

灾备值班员只有一台带机、两盘磁带。本项目用本地文件模拟磁带卷，提供一个 Flask
网页，可以：

1. **巡检带卷**：按带号顺读整卷，逐帧用清单中的 SHA-256 核对，填写“巡检最多
   能读多少帧”；
2. **恢复镜像**：在额度内按块号还原虚拟机镜像；原先的恢复语义保持不变。

巡检与恢复**共用一台带机**：巡检运行中可以接受**一次**恢复插队，恢复结束后
巡检继续把没查完的磁带查完。全部帧核验通过才算查完；遇坏块报位置；额度用尽
仍未查完报额度不足。

## 巡检与恢复语义

### 巡检（`app/inspect.py`）

- **按带号顺读**：先读 tape0 从带头到带尾，再换 tape1，依此类推；每帧都按
  清单 `sha256` 核对。
- **读帧额度**：页面填写“巡检最多读多少帧”。巡检顺读经过的每一帧（含已经
  核验过的帧）都计入巡检实读帧数，额度用尽即停。
- **一次恢复插队**：一轮巡检最多接受一次恢复请求。收到请求后，巡检读完当前
  帧，之后**最多再读两帧**就必须让位；让位前若带卷完好、且单靠巡检能在剩余的
  让位上限与读帧额度内查完，则**必须查完**（不得为了等恢复而无谓让位）。
- **恢复照原额度执行**：插队恢复使用提交时填写的读带/暂存额度，与普通恢复
  完全一致；它实读并核验通过的帧**计入同一套带卷**的巡检（恢复中途失败也
  照算），恢复发现的坏块也会作为本轮巡检的坏块上报。
- **恢复结束后补查**：对仍需补查的磁带**从带头顺读**到该带最后一个未核验帧，
  期间经过的已核验帧同样计入巡检实读量。
- 结果：全部帧核验通过 → 查完；否则报**坏块位置**（镜像块号 + tape + 帧位置）
  或**额度不足**。

### 恢复（`app/engine.py`，原有语义）

- 每套带卷最多两盘磁带、合计最多 12 个 **4 KiB** 镜像块；`manifest.json`
  记录每块的镜像块号、所在磁带、带上帧位置与 SHA-256，每块只出现一次。
- 磁带只能**从头顺读**；换带或回卷后磁头回到第 0 帧。顺读跳过的帧、回卷后
  重读的帧都计入读带量。
- 提前读到、暂时不能按块号写出的块进入**暂存区**，暂存峰值受额度约束；镜像
  只允许按块号 0、1、2…… **顺序追加**。
- 每个块在入暂存前与写出前都核对 SHA-256；坏块或任一额度不足立即中止，
  删除半成品 `.part`，**上一次成品 `image.bin` 原样保留**（原子发布）。

## 页面

- 带卷列表：磁带数、镜像块数、恢复额度预估、上次成品与下载链接。
- **巡检表单**：选带卷 + 填“巡检最多读多少帧” → 开始巡检。
- **恢复表单**：选带卷 + 填读带/暂存额度。巡检运行中提交即为一次恢复插队，
  按钮文案变为“提交恢复插队”；本轮巡检已有插队时再提交返回 409。
- 状态区：巡检**实读帧数**（含经过的已核验帧）、**由恢复补齐的帧数**及具体
  块号、已核验/总帧数、让位次数与每次让位时已读帧数；随后是最近一次恢复的
  用量；最后是事件流。
- `/status`（`/inspection/status` 同义）JSON 含 `inspection_frames_read`、
  `inspection_supplied_frames`、`inspection_complete`、`inspection_status`、
  `inspection`（含 `verified_by_inspection`、`supplied_by_recovery`、
  `bad_block`、`jumps`）等字段。

## 目录结构

```
app/
  storage.py   带卷发现、清单校验、定长帧顺读
  engine.py    恢复引擎：磁头/换带/回卷、读带与暂存额度、逐帧摘要核对、只追加写
  inspect.py   巡检引擎：按带号顺读、帧额度、一次恢复插队、恢复后从带头补查
  web.py       Flask 应用、巡检/恢复后台线程、插队队列、任务状态与成品下载
  templates/   单页界面
scripts/
  make_samples.py  生成三套样例带卷
tests/         引擎/巡检/Web 自测（42 个用例）
run.py         本地开发入口
Dockerfile, docker-compose.yml
```

## 三套样例带卷（`scripts/make_samples.py` 生成）

| 带卷 | 布局 | 恢复读带量 | 恢复暂存峰值 | 巡检帧数 |
|---|---|---|---|---|
| `sample-ordered` | 块号沿顺读方向递增，块 0 在带头 | 12 | 0 | 12 |
| `sample-scrambled` | 每盘带块号沿顺读方向递减 | 12 | 10 | 12 |
| `sample-bad` | 同乱序布局，块 11（tape1 位置 0）数据损坏 | 失败 | — | 报坏块 |

## 本地运行

```bash
pip install -r requirements.txt
python -I scripts/make_samples.py --root data/tapes
python -I run.py
# 或 gunicorn（单 worker 多线程，保证进程内任务状态语义）
python -m gunicorn --bind 0.0.0.0:8000 --workers 1 --threads 4 run:app
```

环境变量：`TAPE_ROOT`（默认 `data/tapes`）、`OUTPUT_ROOT`（默认
`data/output`）、`READ_DELAY`（每读一帧的模拟延迟秒数，默认 `0.05`，设 0 最快）。

## Docker Compose

```bash
docker compose up --build
# 打开 http://localhost:8000
```

镜像内置三套样例带卷；带卷与成品分别挂载在命名卷 `tape-data`、`output-data`
（`/data/tapes`、`/data/output`）。

## 自测

```bash
python -I -m unittest discover -s tests -v
```

覆盖（共 42 个用例）：

- 恢复：顺序/乱序恢复、读带与暂存额度卡线及不足、跳过帧与重读计数、回卷策略、
  坏块检测与块号上报、清单非法（重复块、超 12 块、带文件截断、路径穿越）、
  Web 成功交付与逐块摘要核对、失败保留上次成品、恢复中下载、并发拒绝、非法入参。
- 巡检：纯巡检刚好额度/差一帧、按带号顺序、坏块位置、非法参数；
  **刚好够用额度的巡检 + 中途失败的恢复插队**（恢复核验帧计入、让位前最多再读
  两帧、恢复后从带头补查且经过帧计数、恢复未查完则巡检报额度不足）；
  恢复发现坏块由巡检上报；一轮巡检只接一次插队；请求来迟时巡检必须自己查完；
  不同带卷的恢复核验帧不计入本卷。
- Web：页面上有巡检额度输入、实读帧数与恢复补齐帧数；插队端到端；第二次
  插队 409；巡检/恢复互斥与非法入参。

## 实现、验证与未完成项

### 已实现
- 巡检引擎：按带号顺读、逐帧 SHA-256、独立帧额度；恢复插队（每轮一次）、
  收到请求后最多再读两帧让位、“能自己查完就必须查完”的判定。
- 恢复引擎新增“实读并核验通过的帧”记录（含恢复中途失败时已核验的帧），
  以及坏块的 tape/帧位置，供巡检同步记账/上报。
- 恢复结束后对仍需补查的磁带从带头顺读，经过的已核验帧计巡检实读量。
- Web：`POST /inspect`（别名 `/inspection`）、插队队列与状态接口，页面展示
  巡检实读帧数、由恢复补齐的帧、坏块位置或额度不足原因；原有恢复路径不回归。
- 带卷清单严格校验与恢复原有指标（保持原有 22 个测试全绿）。

### 已验证
- **42 个单元/集成测试全部通过**（`python -I -m unittest discover -s tests`）。
- 关键自测：`sample-ordered` 巡检额度 8 帧 + 读带上限 6 的恢复插队——巡检让位
  前实读 2 帧，恢复核验块 2..5 后因额度耗尽失败，巡检再从 tape1 带头补查 6 帧，
  合计实读 8 帧、恢复补齐 4 帧并查完；额度 7 帧则报“额度不足”。
- 中途失败恢复的已核验帧确实被保留：恢复在块 6 前失败，块 2..5 仍计入巡检。
- 恢复发现坏块（`sample-bad` 块 11 / tape1 位置 0）时，巡检同步报出同一位置。
- gunicorn 单 worker 多线程实际启动；`/`、`/status`、`POST /inspect`、
  `/inspection/status` 均正常，巡检完成后 JSON 字段为
  `frames_read=12, supplied=0, complete=true`。

### 未完成 / 限制
- 本环境无 docker 二进制，`docker compose` 仅做配置静态检查，未实际
  `docker build` / `docker compose up`；Dockerfile 与 compose 未改动的部分
  继续沿用原结构。
- 任务状态保存在单进程内存（gunicorn 固定单 worker）；多副本或重启后任务
  历史不保留（成品文件仍在）。
- 插队请求在巡检“帧边界”被受理：巡检正在读一帧时提交的请求，会在该帧读完
  后才计入“收到请求”，之后最多再读两帧让位；单帧读取耗时受 `READ_DELAY` 影响。
- 巡检只读不写，不校验镜像成品的完整性；成品仍由恢复流程核对并在成功时
  原子发布。
